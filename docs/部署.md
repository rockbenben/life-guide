# 部署（浏览器 / PWA 那条路）

桌面端与手机端都是本地应用，不需要部署。**只有浏览器这条要发布**：
它是一份静态站点，产物在 `app/dist`。

**主地址：<https://life.newzone.top/>**（EdgeOne Pages + 自定义域名）；
**镜像站：<https://rockbenben.github.io/life-guide/>**（GitHub Pages）。
两个地址伺服同一份内容 —— 都从 `gh-pages` 分支取，`deploy.yml` 每次 push 到 main 重新部署。

> **2026-10-29 实测：自定义域名这条通了。** 证书已签发（TrustAsia DV TLS RSA CA 2025，
> `CN=life.newzone.top`，2026-10-28 → 2027-01-26），`curl` 正常 200；
> 把仓库自己的 8 项验收直接跑在这个地址上 —— **8 通过 0 失败**，
> 包括「断网可完整使用一天」（SW 激活、scope = `https://life.newzone.top/`、
> 预缓存 123 项、断网后 13 张卡与 10 张步骤图全在、手册也能离线翻）。
> 镜像站是兜底：从国内取件比 EdgeOne 慢 16 倍（见 §五），首访预缓存要 100 秒左右。
>
> **还差一步**：EdgeOne 线上那份还是 12:02 的构建（见 §三），要在控制台触发一次重新部署。
> **镜像站已经是新构建**（`index-D647rtlj.js`、og:image 指向 `https://life.newzone.top/og.png`），
> 兜底可用 —— 主地址要等 EdgeOne 那边重新部署。

## 一、产物

```bash
npm run app:build          # 内容层构建 + 前端构建，产物在 app/dist
```

`app/dist` 里是一份纯静态站点：

| 文件 | 是什么 |
| --- | --- |
| `index.html` | 入口 |
| `assets/` | JS 与 CSS（文件名带内容哈希） |
| `cards.json` | 518 张卡的结构化数据（约 535 KB） |
| `manual.json` | 手册全文，**只有进「手册」页时才取**（约 811 KB） |
| `media/` | 106 张图片（约 2.1 MB，构建时按显示尺寸重编码） |
| `sw.js` | Service Worker（离线用的） |

**路径全是相对的**（`vite.config.ts` 的 `base: "./"`），所以放在子路径
（`https://life.newzone.top/` 这种根路径，或 `https://…/045/` 这种子路径）都能跑 ——
桌面端的 `app://bundle/` 与手机端的 `capacitor://localhost/` 跑的是同一份产物。

实测过：把 `app/dist` 挂在 `/app/` 子路径下，App 起得来、Service Worker 的 scope
就在子路径、断网重载后卡片与步骤图全在。

## 二、域名：已定 —— `life.newzone.top`

`og:image`（分享出去时的那张预览图）**只认绝对 URL**。构建时给：

```bash
OG_IMAGE_URL=https://life.newzone.top/og.png npm run app:build
```

不给的话落成 `./og.png` —— 本地、桌面、手机都不受影响，但分享到社交平台时那张图会坏。

**现用的地址**：`https://life.newzone.top/og.png`
（已写成仓库变量 `OG_IMAGE_URL`，`deploy.yml` 构建时用它）。

域名选它是因为：

- 跟现有子域名的风格一致（`img.` 是图片、`prompt.` 是那个提示词工具，都是「一个服务一个名字」）；
- 短、好记，跟 App 的名字「生活指南」对得上。

## 三、发布：gh-pages 分支 → EdgeOne（主）/ GitHub Pages（镜像）

跟 `onepage` 同一个模式（那边推 `dist`，这里推 `app/dist`）：

```
push main  →  .github/workflows/deploy.yml  →  构建  →  推 app/dist 到 gh-pages 分支
                                                            ↓
                                     ┌──────────────────────┴──────────────────────┐
                                     ↓                                             ↓
                        EdgeOne Pages 的 Git 集成读这个分支                GitHub Pages 的站点源也是它
                                     ↓                                             ↓
                          <https://life.newzone.top/>              <https://rockbenben.github.io/life-guide/>
                              （主地址，自定义域名）                        （镜像站）
```

**两个地址伺服的是同一份内容**（都从 `gh-pages` 分支取），所以不会出现「一个更新了另一个没更新」。

**EdgeOne（主地址）**：2026-10-29 通了 —— DNS 那条 CNAME 生效
（`life.newzone.top` → `life.newzone.top.pages.dnsoe5.com` → 61.170.82.52），
证书已签发（TrustAsia DV TLS RSA CA 2025，`CN=life.newzone.top`，
2026-10-28 → 2027-01-26），`curl` 正常 200。
**8 项验收在这个地址上全过**（`ACCEPTANCE_URL=https://life.newzone.top npm run acceptance:url`）。
源仓已公开，Git 集成直接读，不用授权 GitHub App。

**但线上那份还是 12:02 的构建**（`assets/index-BQ17IgdM.js`，og:image 还指着镜像站），
而 `gh-pages` 的 HEAD 已经是 `index-D647rtlj.js` ——
**EdgeOne 的同步在 12:02 之后就停了**（12:02 那次推送 2.5 分钟内跟上，
13:19 那次过了 10 个小时没跟上）。
分支本身没错（实测它给的那份与 `gh-pages` 12:02 的产物逐字一致，sha256 相同），
所以要的是**在控制台里触发一次重新部署**，不是换分支。
判据：对比线上 `index.html` 的 sha256 与 `gh-pages` HEAD 那份
（`raw.githubusercontent.com` 能取到任意一次提交的内容，直接比哈希最省事）。

源仓已公开，Git 集成直接读，不用授权 GitHub App。

**2026-10-29 早上又查了一次，机制查清了（换分支没用，是取分支那一步没跑）**：

- **EdgeOne 不重新构建**，它伺服的就是 `gh-pages` 分支里的那份文件树 ——
  实测线上 `sw.js` 与 `gh-pages@ccdcb67:sw.js` **逐字节相同**，
  `index.html` 的 sha256 也与那个提交一致（`BEC9A130…`）。
  所以「EdgeOne 自己 build 失败了」这个猜测不成立：它压根没 build。
- **不是 CDN 缓存压着旧文件**：`EO-Cache-Status: Cache Hit` 但加随机 query
  （`?cb=…`）去拿，拿到的还是旧的；新资源 `assets/index-D647rtlj.js` 直接 404。
  边缘节点背后就是这份旧树。
- **不是「没有新推送所以没触发」**：13:19 那次是真的推了新提交（`cbb26f0`），
  之后又推了一个**空提交**（树不变、内容不变，只为了让 EdgeOne 的分支监视器
  再收到一次 push 事件）—— 线上仍旧没变。
  ⇒ **是 EdgeOne 侧取分支那一步停了**，只能去控制台点重新部署。
- 顺带查清了一件容易误判的事：**后两次 deploy（23:23、23:55）其实没推任何东西** ——
  `JamesIves/github-pages-deploy-action` 打出 `There is nothing to commit. Exiting early`，
  因为那两次只改了文档，`app/dist` 与分支上已有的逐字相同。
  ⇒ **`gh-pages` 上最后一次真正变更就是 13:19 那次**，之后分支一直停在 `cbb26f0`。
  看 GitHub 上「分支有没有更新」容易被这一点误导。
- **`edgeone` CLI 装在本机**（`edgeone@1.0.27`，`pages deploy <dir> -n <项目名>`），
  但要 `edgeone login`（浏览器交互）才能用，`pages-api.edgeone.ai` 也没有免登录的查询口。
  所以命令行这条路也得用户先登录。

**GitHub Pages（镜像）**：站点源就是 `gh-pages` 分支，公开仓的 Pages 免费，HTTPS 强制开。
留着它是因为它不依赖任何第三方 —— EdgeOne 那边出问题还有个兜底。

**仓库这边已经就绪**（`.github/workflows/deploy.yml`）：
push 到 main 就构建并把产物推到 `gh-pages` 分支（`JamesIves/github-pages-deploy-action@v4`，
`clean: true` 先清空分支）。也可以在 Actions 里手动跑。

**这个工作流已启用**（2026-10-28）—— push 到 main 就重新部署，不用再动设置。

EdgeOne 那边要配的三件事（**已配好**，记在这里是为了换域名时照着做一遍）：

1. **Git 集成**：连 `rockbenben/life-guide`，分支选 `gh-pages`。
   **源仓已公开（2026-10-28），EdgeOne 的 Git 集成可以直接读**；
   万一又要转私有，就得授权那个 GitHub App，或者给一个只读这个仓的 token；
   都拿不到就退一步：把 `gh-pages` 分支的内容下载下来，用控制台直传上传。
2. **自定义域名**：`life.newzone.top`，DNS 加一条 CNAME 指向 EdgeOne 给的地址。
3. **构建设置**：如果 EdgeOne 直接伺服分支里的静态文件（推荐，分支里已经是构建产物了），
   不用填构建命令；如果 EdgeOne 要自己构建，填：
   - 构建命令：`npm ci && npm run app:build`
   - 输出目录：`app/dist`
   - 环境变量：`OG_IMAGE_URL=https://life.newzone.top/og.png`

**og:image 的绝对地址**在**构建时**就要给（`OG_IMAGE_URL` 环境变量，
`app/vite.config.ts` 会替换 `index.html` 里的占位符）。workflow 里已经写了默认值
`https://life.newzone.top/og.png`，也可以在仓库 Settings → Variables 里设
`OG_IMAGE_URL` 覆盖它。域名换了就改那一个值。

## 四、发完要验的四件事

1. **打开就是今天页**（不是白屏 —— 白屏多半是路径或 SW 的问题）；
2. **「手册」页能进去**（`manual.json` 是懒加载的，第一次点「手册」才会取）；
3. **断网重载还能用**（DevTools → Network → Offline，刷新，卡片与步骤图都还在，
   数量与联网时一致）；
4. **分享出去有预览图**（og:image 是绝对地址才成）。

前三条 `npm run acceptance` 里就有对应的脚本（在本地根路径下跑）；
**要验线上那个地址**用 `ACCEPTANCE_URL=https://life.newzone.top npm run acceptance:url`
—— 同一套检查直接跑在真实域名上（不起本地服务器），证书、SW scope、
预缓存这些只有真域名才说得清的东西才验得到；
第四条得用真实域名看。

## 五、别踩的坑

- **别把 `app/public/cards.json` 提交进 git** —— 它是构建产物（`.gitignore` 已经管了），
  而且每次内容层改动都会变。发布的是 `app/dist`。
- **别在发布前手动改 `app/dist` 里的东西** —— 下次构建就没了。
- **子路径部署时别把 `base` 改回 `"/"`** —— 图片会全部 404（`/media/x.png` 指的是域名根）。
- **SW 的缓存是按内容哈希算的**：内容没变时用户不会重下 1.3 MB；
  但如果产物里带了随时间变的字段（比如构建时间），每次发布用户都要重下全部数据 ——
  所以 `builtAt` 不进产物（`content/src/build.ts`）。
- **源仓公开时**：EdgeOne 的 Git 集成可以直接读（本仓 2026-10-28 已转公开）；
  万一转回私有就要授权 GitHub App 或给只读 token，都拿不到就把 `gh-pages`
  分支下载下来，用控制台直传上传。
- **分享文案里的卡片数是构建时现算的**（`app/vite.config.ts` 的 `shareMeta` 读
  `app/public/cards.json`）—— 写死的话，每签一轮字就又是一个假数字。
- **验自定义域名要连 Service Worker 一起验。** 页面 200 不等于域名通了：
  证书不对时页面照样渲染得出来（强制忽略证书就能开），
  但浏览器会拒绝带证书错误的 SW 脚本，离线功能整个没有。
  判据是 `navigator.serviceWorker.ready` 能不能等到 `activated`
  —— 更省事的是把仓库那套验收直接跑在那个地址上
  （`ACCEPTANCE_URL=<地址> npm run acceptance:url`）。
- **EdgeOne 的 Git 同步不是实时的。** 12:02 那次推送 2.5 分钟内跟上了，
  13:19 那次过了 10 个小时没跟上。发布后要看一眼线上给的是不是新构建 ——
  对比线上 `index.html` 的 sha256 与 `gh-pages` HEAD 那份（`raw.githubusercontent.com`
  能取到任意一次提交的内容，直接比哈希最省事）。
  **别被分支的 commit 时间骗了**：`deploy.yml` 打出 `There is nothing to commit` 时
  其实**没推任何东西**（产物与分支上已有的逐字相同），分支会一直停在最后一次真正变更的提交上。
- **GitHub Pages 镜像从国内取件慢一个量级。** 同一批 11 个文件：
  EdgeOne 平均 **0.16 s/件**，GitHub Pages 平均 **2.66 s/件**。
  PWA 首访要预缓存 123 项，镜像站上 SW 装完要 **98.7 秒**
  （实测：78.7 s 时缓存了 94 项，98.7 s 满 123 项并激活），期间还不算「离线可用」。
  镜像是兜底，不是主体验 —— 主地址该走 EdgeOne。
